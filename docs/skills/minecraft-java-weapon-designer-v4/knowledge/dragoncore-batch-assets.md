# 大型 DragonCore 资产库的工程经验

以下内容是从用户拥有的批量资源中提炼的非表达性工程规律，不包含原始美术或模型文件。

## 主要结论

- 大型包的性能瓶颈可能来自动画贴图总量，而不是单个模型的元素数。
- 同一套装的多个编号目录经常复制相同 PNG 与 `.mcmeta`。
- 状态模型可能与主模型并列存放，因此只搜索 `model.json` 会漏掉重要内容。
- 零厚度元素常被用于火焰、光效、符文和翼面；它不是自动错误，但容易产生 Z-fighting 与透明排序问题。
- 完整 Blockbench 模型常用 0、±22.5、±45 度单轴旋转。
- `head`、左右手、GUI、ground 和 fixed 的变换应作为独立资产质量指标。
- 中文路径可以在现有生态中工作，但跨 Linux、自动化脚本和其他插件迁移时更容易出错。

## 优化顺序

1. 修复解析和缺失引用。
2. 修复客户端/服务端映射。
3. 修复动画元数据。
4. 确认状态模型触发。
5. 做运行时抽样测试。
6. 最后才进行资源集中、去重和 ASCII 迁移。

## 去重边界

相同内容并不代表可以安全删除。若模型使用当前目录短名，加载器可能要求每个编号目录保留一份贴图。去重必须先验证共享路径是否被当前 DragonCore 版本支持。
